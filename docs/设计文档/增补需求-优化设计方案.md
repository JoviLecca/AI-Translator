## 1. 振假名子系统设计

### 1.1 现状与问题

- 现有占位符体系（设计 §7.1）保护的是"不可译内容"（行内代码/URL/图片），振假名相反：**基词要参与翻译，注音要按策略处理**，不能整体当占位符塞掉——否则基词脱离句子语境，译文必然生硬；
- 四种格式的振假名形态完全不同（见 1.2），需要各自检测、统一内部表示、各自还原；
- 术语归纳（阶段一频次统计）若把注音当正文，会产生大量假名垃圾候选。

### 1.2 振假名形态盘点（检测范围）

| 来源格式 | 形态 | 示例 | 默认识别 |
|---|---|---|---|
| md / txt | 青空文库式 `基词《注音》` | `漢字《かんじ》`、`一廣《かずひろ》` | ✅ 严格（默认开） |
| md / txt | 全角括号疑似式 `基词（注音）`，注音为纯假名 | `魔法（まほう）` | ⚠️ 宽松（默认关，项目开关；括号内可能是真括注，误报代价高） |
| html | 原生 `<ruby>基<rt>注</rt></ruby>`（含 `<rp>` 变体） | `<ruby>魔法<rt>まほう</rt></ruby>` | ✅ 结构化解析 |
| docx | 原生 `w:ruby`（`w:rubyBase` + `w:rt`） | XML 元素 | ✅ 结构化解析（python-docx 无 API，走 lxml 遍历 run 内 XML） |

检测正则（严格式）：`([\u4e00-\u9fff々〆\u30A0-\u30FFーA-Za-z0-9]{1,20})《([^》\n]{1,30})》`，
基词与注音均为非空、注音长度 ≤30；同一行内允许多个构造。

### 1.3 内部统一表示

适配器 parse 时，每个振假名构造拆解为：

```
基词（保留在段平文本中，参与翻译）
  + 注音槽 token：{r0}、{r1}……（紧跟基词之后，独立命名空间，与 {0} 占位符互不冲突）
  + 块级元数据：meta["ruby"] = [
      {"token": "{r0}", "base": "漢字", "rt": "かんじ",
       "style": "aozora|paren|html|docx"} ]
```

- token 正则 `\{r(\d+)\}`；现有 `placeholders_ok` 校验扩展为按策略校验 `{rN}`（见 1.5）；
- 导入与导出**重放同一确定性检测**（与分段同理，保证 seq 对齐稳定）；
- 段内既可有 `{0}` 保护占位符又可有 `{rN}` 注音槽，编号各自独立。

### 1.4 策略模型（项目级设置 `ruby_policy`）

| 策略 | 语义 | Prompt 指令 | 译文校验 | 渲染还原 |
|---|---|---|---|---|
| `drop` | 注音无意义（默认：目标语为 zh/en 时） | 删除所有 {rN} token | 译文中不得残留任何 {rN}；残留则程序剥离 + 标待复核 | 无（token 消失即还原） |
| `keep` | 保留原注音（特殊读法效果，默认：目标语为 ja 时） | token 原样保留、紧贴译词 | token 集合与源文一致；缺失→单段重译→仍缺则补回原位 + 待复核 | token → 原格式注音（`《かんじ》`/`（かんじ）`/`<rt>かんじ</rt>`/w:ruby rt），注音**原文不动** |
| `translate` | 注音本身也翻译/转写（轻小说双关、异读效果） | token 保留，并在 JSON 中为每个 token 给出目标语注音 | token 集合一致；`ruby` 字段缺失的 token → 单段重译一次 | token → 原格式注音，内容用**译注音** |

- **单次调用完成**：translate 策略下响应 JSON 扩展为
  `{"translations":[{"id":..,"t":"..","ruby":{"r0":"译注音"}}]}`，解析容错链复用现有三级策略；
- **auto 默认值**：新建项目按目标语预填（ja→keep，其他→drop），用户可改；
- 体裁影响（如轻小说的"汉字写A读B"修辞）不单独建策略，由 translate 策略 + 文件标签
  （作品类型=轻小说）在指令中体现，避免策略矩阵膨胀。

### 1.5 引擎与 Prompt 改动

- `prompt_builder.translation_system`：**条件块**——仅当批次文本含 `{rN}` 时注入振假名
  说明与策略指令（非日文/无振假名项目 prompt 完全不变，零开销）；
- `parse_translations`：新增可选 `ruby` 字段解析（缺省容错）；
- 引擎校验链（设计 §7.5 译文合理性校验）追加：
  - drop：`{rN}` 残留 → 剥离 + review_flag；
  - keep：token 丢失 → 单段重译 → 仍丢 → 在译词后补回 `《原注音》` + review_flag（保底不断稿）；
  - translate：token 丢失同上；`ruby` 译文缺失 → 该 token 降级为 keep（原注音）+ review_flag；
- **持久化**：segments 表新增 `ruby_map TEXT`（schema v2 迁移，自动升级），
  存 `{token: 译注音}`；导出时引擎译文 + ruby_map 一起喂给渲染器。

### 1.6 各适配器渲染还原

| 格式 | drop | keep / translate 还原 |
|---|---|---|
| md/txt | 无动作 | token → `《rt'》`（aozora 式）或 `（rt'）`（paren 式），按 parse 记录的 style |
| html | 无动作 | 锚定 token 前最近的内联文本节点为译词，包成 `<ruby>译词<rt>rt'</rt></ruby>`；无法锚定（token 位于行首等）→ 降级括号注音 + review_flag |
| docx | 无动作 | 阶段一（R1）：`（rt'）` 括号式并记为已知边界；阶段二（R3 可选）：复制原 `w:ruby` XML 节点、替换 base/rt 文本实现原生还原 |

> html/docx 的"向前锚定译词"是本方案唯一带启发式的环节，失败路径均有兜底且打待复核标记，
> 与既有"译文解析失败保留原文"的兜底哲学一致。

### 1.7 与既有机制的联动

| 机制 | 影响 |
|---|---|
| cfg_hash | `ruby_policy` **纳入**有效配置指纹（策略改变输出形态，旧译文必须失效；改宽松识别开关同此） |
| 翻译记忆 / 运行内去重 | 无结构变化：振假名 token 在 src_text 内，src_hash 自然区分不同构造 |
| 术语归纳（阶段一） | 候选抽取前剥离 `{rN}` token 与《》注音，只用基词文本，防假名垃圾候选 |
| 术语一致性报表 | 不变（扫描的是 tgt_text） |
| 成本预估 | 含振假名批次 prompt 略增（策略块 + ruby 字段），预估系数 1.2→1.25 微调 |

### 1.8 UI 与配置

- 项目设置页新增：**振假名策略**下拉（drop/keep/translate，显示推荐默认）+
  **宽松识别（全角括号假名）**复选框 + 修改时的缓存失效提示（复用现有 cfg 变更弹窗）；
- 新建向导第 2 步（语言方向页）追加该两项（目标语为 ja 时默认 keep，否则 drop）；
- project.json 增 `ruby_policy`、`ruby_loose` 两键。

### 1.9 测试计划

- 单元：检测正则（多构造/边界长度/全半角）、token 命名空间不与 `{0}` 冲突、
  三策略校验链（drop 残留剥离、keep 丢失补回、translate 缺 ruby 降级）、schema v2 迁移；
- 黄金文件：md（aozora 式）、txt（宽松式开/关）、html（`<ruby>`+`<rp>`）、docx（括号式边界）
  各一份 `parse → render` 往返，断言三种策略下的注音形态与结构零丢失；
- 验收（R1）：以本次实测的《第１話》章节注入振假名样例（`一廣《かずひろ》`、
  `<ruby>魔法<rt>まほう</rt></ruby>`），GLM 真跑三策略端到端，
  drop 输出无注音、keep 假名原样、translate 注音为中文且 md/html 格式还原。

## 2. 上下文滑窗设计（slide 选项）

### 2.1 现状

引擎目前只带**前向**上下文：批次开始前同文档的 `context_n`（0~5，全局设置）
段**已定稿译文**（设计 §7.3）。缺口：① 无后文（后视）——代词指代、悬念呼应、
对话轮次经常需要"知道下一段说什么"；② 参数是全局而非项目级。

### 2.2 滑窗语义与批级实现的等价性

需求定义：段级滑窗 N = 翻译某段时可见其前 N 段与后 N 段。

实现取**批级滑窗**：批次（同文档连续 ≤10 段）取
`前文 = 批首之前 N 段（已定稿译文优先）`、`后文 = 批尾之后 N 段（源文）`。

等价性论证：批内任意段与其前后邻居同批可见（天然满足窗内需求）；
批首段缺前文 → 前文块补足 N 段；批尾段缺后文 → 后文块补足 N 段；
中间段两侧批内邻居均 ≥N。故**每个段落实际可见的前后文 ≥ N 段**，
与逐段单独开窗效果等价，而请求数不变（零成本升级）。

### 2.3 上下文来源优先级

| 方向 | 内容来源 | 理由 |
|---|---|---|
| 前文 | confirmed > human_edited > machine_translated 的**译文**；无任何译文（首跑）→ 源文并标注"（源文）" | 已定稿即"上文既成事实"，保证术语与行文承接 |
| 后文 | **源文**（尚未翻译） | 后文只用于消解指代与预告伏笔，不存在译文 |

前后文均以 `· ` 前缀逐行渲染，结构上不可能命中 Mock/解析器的 `#id` 段标记，
且 prompt 明示"前后文仅供参考衔接，禁止翻译、禁止输出"。

### 2.4 Prompt 结构（translation_user 扩展）

```
【前文（已定稿，仅供衔接，不得翻译或输出）】
· （最多 N 行译文）
【后文（源文，仅供衔接，不得翻译或输出）】
· （最多 N 行源文）
【待译段落】
#12 ……
```

`context_n=0` 时不注入任何上下文块，prompt 与现状逐字节一致（回归保证）。

### 2.5 成本与上限

- 每批增量 ≈ 2N 段（CJK 约 2N×120 字 ≈ 240N 字符）；N=2 时约 +9% prompt；
- 硬上限：前后文合计 ≤3000 字符，超出从最远端截断（保近邻）；
- `costs.estimate_run` 增加 slide 参数：输入开销系数 `1.2 + 0.05×N`（上限 1.6 不变）。

### 2.6 配置与 cfg_hash 决策

- 新键：project.json `context_slide`（0~5，缺省继承全局 `context_segments`，
  全局项文案改为"默认上下文滑窗段数（前 N + 后 N）"）；
- **不纳入 cfg_hash**：slide 是质量倾向旋钮而非输出形态契约——纳入会导致用户每次微调
  就全书缓存失效、触发大规模重译费用；与 ruby_policy 的差异在于：振假名策略改变的是
  译文的**构成**（注音有无/语言），slide 只改变翻译时的参考信息量。
  用户调整 slide 后想重刷质量，走已有的"重译过期机器译稿"入口；
- 预检对话框展示当前 slide 值，让用户在开始前对成本有感知。

### 2.7 代码落点与测试

- `engine._context()` 扩展后视查询（`seq > 批尾`，translatable=1，升序 LIMIT N）；
- `prompt_builder.translation_user(batch, before, after)`；Mock Provider 的段解析不变；
- 项目设置页 spinbox；向导第 2 步可选暴露（默认隐藏，进阶项）；
- 测试：①单测断言 N=1/2 时 prompt 含正确的前后文行（用 Mock 捕获 messages）；
②N=0 时 prompt 与旧版一致（快照回归）；③前文优先级（人工改稿后二跑，前文取 human_edited）；
④验收：以《第１話》对话密集段做 N=2 对比 N=0 人工抽检（指代、语气连贯）。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 漏掉/移动 {rN} token | 三级兜底：批校验→单段重译→程序补回原位 + 待复核（不断稿） |
| translate 策略下注音译文质量差（脱离整句语境） | ruby 字段要求 LLM 结合该段译文给注音；待复核标记覆盖；用户可在校对页直接改 ruby_map（R3：校对页注音内联编辑） |
| 全角括号宽松识别误伤真括注 | 默认关；开启后疑似构造在校对页以浅色标注，可一键"当作普通括号"（段级例外表） |
| 后文注入诱发 LLM 越权翻译后文 | `· ` 前缀 + 显式禁令 + 输出按 id 严格匹配（多余 id 一律丢弃，现有机制） |
| slide 增大单批 prompt 触发上下文超限 | 3000 字符硬上限 + 批内字符预算不含上下文（上下文按开销系数另行预留） |
| schema v2 迁移破坏旧项目 | 复用启动自动迁移（NFR-08），迁移测试纳入 R1 |
