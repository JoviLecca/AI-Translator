> 面向接手开发的工程师。目标：读完本文能定位任何一处改动该落在哪个文件、

## 1. 一句话定位

以「项目（=一个文件夹）」为单位的**桌面端 AI 辅助翻译工具**：
导入 → 分段 → 术语归纳 → AI 批量翻译 → 双栏校对 → 多格式导出。

- 运行形态：PySide6 桌面应用，纯本地（无后端服务），唯一外联是用户自己配置的 LLM API；
- 技术栈：Python 3.12（设计要求；本机实测 3.14.7 亦能 import 全部依赖）/
  PySide6-Essentials / SQLite(WAL) / httpx / lxml /
  markdown-it-py / python-docx / keyring / rapidocr-onnxruntime / jieba；
- 入口：`main.py`（`python main.py` 启动 GUI，`python main.py --selftest` 离屏冒烟 6 页面）。

## 2. 分层架构与依赖方向

依赖**只允许自上而下**，反向依赖会破坏可测试性（引擎不能 import UI）。

```
┌─ app/       UI 层（PySide6，6 页面 + 若干对话框）
│    context.py（AppContext 服务容器 + Bridge 跨线程信号）
│    main_window.py（侧栏导航 + QStackedWidget）
│    pages/*（页面）
├─ core/      应用服务层 + 领域层（不依赖 PySide6）
│    pipeline.py（ImportService / TranslationService / ReviewService / ExportService）
│    engine.py（RunEngine：批量翻译执行引擎，asyncio）
│    project.py（Project：文件夹、锁、cfg_hash）
│    glossary.py / term_induction.py / term_impact.py / consistency.py
│    segmentation.py / styles.py / costs.py / appconfig.py
├─ adapters/  文件格式适配层（IFormatAdapter：parse + render）
│    __init__.py（格式注册表）  base.py（DocumentModel/Block/占位符契约）
│    txt / md / html / docx / epub / srt / ocr adapter  +  ruby.py（振假名子系统）
├─ llm/       LLM Provider 抽象与实现
│    provider.py（ILLMProvider / Message / LLMResult）  prompt_builder.py（Prompt + 解析）
│    openai_compat.py / anthropic_provider.py / gemini_provider.py / mock.py / errors.py
└─ storage/  基础设施
     db.py（SQLite WAL + RLock 串行写 + schema 迁移）  secrets.py（keyring）
```

**UI 与引擎分离**是硬约束：翻译跑在后台 `threading.Thread` 里的独立 asyncio loop，
UI 线程只通过 Qt 信号 `Bridge.progress / run_done / toast` 收状态，绝不直接读引擎对象。

## 4. 一次翻译的完整数据流

```
① 导入   ProjectsPage/WorkbenchPage → ImportService.import_file(src)
         ├ copy2 进 <project>/source/
         ├ detect_format → get_adapter(fmt).parse()  →  DocumentModel(blocks)
         ├ 每 block 算 src_hash = sha256(text.strip())
         │     block 里 text 已做：内联元素→{0}占位符、振假名基词+{rN}注音槽
         └ db.upsert_document() → db.replace_segments(doc_id, blocks, cfg_hash)
               ↑ 整体 DELETE 后重建；按 src_hash+cfg_hash 从**别的文档**回填旧译文(TM)

② 归纳   InductionService.run()（core/term_induction.py）
         ├ 阶段一（本地免费）：按 src_lang 抽候选（zh=jieba，ja=片假名串+汉字bigram，其他=拉丁词）
         └ 阶段二（LLM）：每 40 个候选一批送判定 → terms 表 status='candidate'
               → 术语审核对话框（app/pages/terms_dialog.py）人工确认 → 写 glossary.csv

③ 预检   TranslationService.precheck()
         ├ 外部改过 glossary（mtime/size 变）→ 自动重载
         ├ 统计 pending/failed 段数与字符数、stale_translations（cfg_hash 不一致的已译段）
         └ costs.estimate_run() 给 token 预估 → UI 弹确认

④ 翻译   TranslationService.start() → threading.Thread → RunEngine.run_translation()
         ├ ① TM 预检：src_hash+cfg_hash 命中且非本文档 → 直接回填，不花 API
         ├ ② 运行内去重：同 src_hash 只送翻一次，结果回填所有重复段
         ├ ③ 分批判：同文档连续、≤10 段 且 ≤4000 字符
         ├ ④ asyncio.Semaphore(concurrency) 并发；每批取上下文滑窗
         ├ ⑤ provider.chat(json_mode=True) → prompt_builder.parse_translations_full
         ├ ⑥ 逐段校验（空译/照抄源文/占位符不符/振假名 token 缺失）→ 可疑段单段重译
         └ ⑦ 落库 status='machine_translated'，review_flag 标待复核；进度写 runs/run_items

⑤ 校对   ReviewPage（双栏）→ ReviewService.edit / confirm / search_replace
         编辑即 human_edited；确认即 confirmed

⑥ 导出   ExportService.export(doc_ids, mode, output_format)
         ├ 源文件 hash 变更 → 警告并拒绝（除非 force）
         ├ 重新 parse 源文件（保证 seq 对齐）→ translations = {seq: tgt_text}
         └ adapter.render(out, model, translations, mode='target'|'bi_inter'|'bi_table')
               → <project>/target/<原名>.<目标语后缀>.<扩展名>
```

## 5. 数据模型（`.aitrans/work.db`，`SCHEMA_VERSION = 2`）

| 表 | 用途 | 关键列 |
|---|---|---|
| `meta` | 版本 | `schema_version` |
| `documents` | 已导入源文件 | `path` UNIQUE（相对根）、`format`、`content_hash`、`tags`(JSON)、`terms_extracted`、`status` |
| `segments` | 分段与译文（核心） | `seq`、`src_text`、`src_hash`、`tgt_text`、`status`、`is_heading`、`translatable`、`cfg_hash`、`review_flag`、`ruby_map`、`ruby_src` |
| `terms` | 术语缓存/归纳中间态（**权威数据是 glossary 文件**） | `src_term` UNIQUE、`tgt_candidates`（`a\|b\|c`）、`origin`、`status`(candidate/approved/rejected)、`occurrences` |
| `terms_revision` | 术语表快照（供变更影响分析 diff；只比对最近两份） | `payload`(JSON) |
| `runs` / `run_items` | 任务与断点续翻依据 | `type`(terms/translate)、`status`、`done/failed`、`tokens_in/out`、`cost` |

索引：`(doc_id,seq)` 校对列表、`(src_hash,cfg_hash)` 翻译记忆、`(status)` 过滤。

**术语快照的写入纪律**（术语变更影响分析只比对最近两份快照，写错就会比不出差异）：

| 时机 | 入口 |
|---|---|
| 打开项目 | `Project.open()` → `snapshot_terms(only_if_changed=True)`（记基线） |
| 软件内增/删/改/合并术语 | 工作台 `_snapshot_terms()` → `Project.snapshot_terms()` |
| 外部（Excel）改过之后重载 | `Project.reload_glossary()`：先补"改之前"、重读文件、再记"改之后" |
| 术语归纳审核通过 | `InductionService.approve()` → `save_terms_revision()` |

内容没变时**不写重复快照**（`only_if_changed`）——否则「上一次真实变更」会被挤出
只比最近两份的窗口。`Project.open()` 之后即便用户在外部改完直接重开项目，
也能比出差异。

**段落状态机**（`storage.db.SEG_STATUSES` 是白名单，`update_segment` 会 assert）：

```
pending ──机翻成功──▶ machine_translated ──人工编辑──▶ human_edited ──确认──▶ confirmed
   └──失败──▶ failed ──重试──▶ pending
```

### 5.1 两条缓存语义（最容易踩的雷）

**`src_hash`** = 段落文本的 sha256（`.strip()` 后）。键 + 值都存 `segments`。

**`cfg_hash`** = `sha256(json({"style","custom","tgt","terms"[, "ruby"]}, sort_keys))`
（`core/project.py::cfg_hash`）：

- 含：风格预设、自定义风格、**目标语**、**术语有效集合**、以及**非默认时**的
  `ruby_policy|ruby_loose`；
- **不含**：源语、Provider、模型、`context_slide`、文件标签、术语注释。

设计意图（改动前务必理解）：
- 改术语**注释**不失效缓存 → `Glossary.effective_hash()` 只哈希 `源词 + 候选序列`；
- 换 Provider/模型不失效 → 避免换模型导致全书重译；
- 默认振假名策略（drop + 宽松关）**不写入指纹** → 旧项目升级后缓存不失效；
- `context_slide` 不写入 → 它是质量旋钮，纳入会导致每次微调就全书重译。

**翻译记忆（TM）** 只在 `status IN (confirmed, human_edited, machine_translated)` 且
`tgt_text` 非空、`doc_id != 当前文档` 时命中；优先级 confirmed > human_edited > machine_translated。

### 5.2 `replace_segments` 的语义

同名文件重导入 = **该文档段记录整体 DELETE 后重建**，重建时按 `src_hash+cfg_hash`
从**其它文档**回填译文。所以：

- `seq` 漂移无害（对齐靠重新 parse 的确定性分段算法）；
- 导入端与导出端必须重放**同一套确定性 parse**，否则 seq 错位；
- `translatable=0` 的透传段 `cfg_hash` 存 NULL。

迁移：v1 → v2 增加 `segments.ruby_map` / `ruby_src`（`_migrate` 里
`PRAGMA table_info` + `ALTER TABLE`，幂等）。**加字段必须同步升 `SCHEMA_VERSION`
并写迁移分支 + 迁移测试**（参考 `tests/unit/test_migration.py`）。

## 6. 六个关键机制

### 6.1 占位符保护 `{0}`（不可译内容）

`adapters/base.py::ProtectMap`：适配器把行内代码 / URL / 图片等替换为 `{n}`，
译文回来后 `restore()` 还原。引擎用 `placeholders_ok(src, tgt)` 校验
**数量与顺序一致**，不符则该段标 `review_flag` 并重译一次。

`effectively_empty(text)`：剥离占位符与所有 Unicode 空白（含零宽）后为空 → 视为透传段，
不进翻译队列、不耗 API。**空白段绝不能参与 TM/去重**（否则一条译文会被回填给全部空白段，
这是历史缺陷 #2/#3，见 `test_engine_blank_segment_no_api_no_repeat`）。

> ⚠️ **`{0}` 与 `{r0}` 在校验层并未真正隔离**。`tokens_of` 用的
> `_TOKEN_RE = re.compile(r"\{r?(\d+)\}")` 只捕获数字、丢掉 `r` 前缀，实测：
> `tokens_of("{r0}") == tokens_of("{0}") == ["0"]`，于是
> `placeholders_ok("{r0}", "{0}")` **返回 True**——模型把注音槽换成保护占位符
> （或反之）能通过校验。`ruby.py` 注释所称"独立命名空间互不冲突"对
> **替换/还原**成立，对**校验**不成立。详见 §10.11 ①。

### 6.2 振假名 / 注音 `{rN}`（最微妙的子系统）

与 `{0}` **独立命名空间**。`adapters/ruby.py` 是纯函数层，各适配器负责调用与还原。

- 检测（`rubyize_text` / 各适配器）：`《》` 青空文库式（默认开）、全角括号纯假名式
  （`ruby_loose` 开关，默认关）、**markdown/html 内联 `<ruby>基<rt>音</rt></ruby>`**
  （含 `<rb>` / `<rp>` / 属性变体，`rubyize_text(html=True)`）、docx `w:ruby`（结构化解析）；
- 内部表示：**基词保留在平文本参与翻译** + 紧跟其后插 `{rN}` 槽 +
  `meta["ruby"] = [{token, base, rt, style}]`，落库到 `segments.ruby_src`；
- 三策略（项目级 `ruby_policy`，可被文件标签 `tags["ruby_policy"]` 覆盖，
  见 `engine._policy_for`）：

| 策略 | Prompt | 引擎校验链（`engine._finalize_ruby`） | 渲染 |
|---|---|---|---|
| `drop` | 删除全部 `{rN}` | `strip_ruby_markup`：残留 `{rN}` **与 `<ruby>` 标记**一起剥离 + `review_flag` | 无动作（导出前再兜底清理一次，见下） |
| `keep` | 原样保留、紧贴译词 | token 丢失 → 单段重译 → 仍丢则补回 `《原注音》` + `review_flag` | 还原原假名 |
| `translate` | 保留 + JSON 返回 `ruby` 字段 | 同 keep；`ruby` 缺该 token → flag（渲染回退原假名） | 还原**译注音**（存 `segments.ruby_map`） |

加固点（审查第 2 轮）：伪造/未知 token 一律删除、重复 token 折叠为一次，均打 `review_flag`。
`_finalize_ruby` 的兜底哲学是**保底不断稿**：宁可注音回退原文，也不能让段落失败。

**drop 的契约是「译文里不出现 ruby 格式」**，因此在三个位置强制：

1. `engine._finalize_ruby` 的 drop 分支 → 落库即干净（新翻译）；
2. `ExportService.export` 对 drop 文档的 `translations` 再兜底清理一次 →
   **修复前导入的旧项目、库里已带标签的旧译文，无需重新翻译，重新导出即可**；
3. keep / translate 不做任何清理（`test_drop_policy_removes_ruby_markup_entirely`
   反向断言了这点）。

**原生还原的锚定启发式**：markdown / html 的 `<ruby>` 还原要把 `{rN}` 前面的
**译词**重新包进 `<ruby>`（`restore_ruby_native`）。东亚文字无词间空格，贪心锚定会把
前面的词一起卷进基词（日语 `彼は魔法`；中文目标更极端，`他使用了魔法` 全是汉字，
按字符类无法区分），因此以**源基词长度**为上界截短；纯拉丁串按整词处理不截短。
锚不到译词时降级为 `（注音）`，与既有兜底一致。

> **四种格式已统一**：md / html / epub / docx 的原生还原都走 `split_anchor_hint`
> （原来是 html/docx 用贪心版 `split_anchor`、md 用截短版，行为不一致）。
> 旧的 `split_anchor` 因此已删除 —— `split_anchor_hint(text)` 不传 `src_base` 时
> 就等于它原来的语义。`test_ruby_adapters.py::test_html_ruby_native_restore` 的
> 断言也随之从「`彼の名は一廣` 整串进 `<ruby>`」改为正确的「只有 `一廣` 进」。

### 6.3 上下文滑窗（`context_slide`）

批级实现（`engine._context_blocks`）：前文 = 批首之前 N 段的**已定稿译文**
（confirmed/human_edited/machine_translated，按 seq 降序取再反转）；
后文 = 批尾之后 N 段的**源文**。前后合计 ≤ `MAX_CONTEXT_CHARS = 3000`，
超出从**最远端**截断（保近邻：前文删头、后文删尾）。

等价性论证（增补设计 §2.2）：批内任意段的批内邻居 ≥N，批首/批尾由批外补足，
故每段实际可见前后文 ≥N，与段级滑窗等价而请求数不变。

`context_n = 0` 时 `translation_user` 不注入任何上下文块，Prompt 与旧版**逐字节一致**
（回归保证，`test_slide_zero_no_context_blocks`）。

取值优先级：`project.context_slide`（None 表示继承）→ 全局 `cfg["context_segments"]`，
夹取到 0..5（`TranslationService.slide()`）。

### 6.4 翻译记忆 + 运行内去重（省钱的两条腿）

- **跨文件 TM**：`db.find_tm(src_hash, cfg_hash, exclude_doc)` 在引擎 TM 预检阶段回填；
- **运行内去重**：同一次 Run 内相同 `src_hash` 只送翻一次，结果回填所有重复段
  （`stats["dedup"]`）。**但跨 Run 不共享**——下次运行会再走 TM 预检。

成本：`core/costs.py` 只做 **token 预估**（价格字段与费用统计已下线，反馈 #6）。
`estimate_run(src_chars, slide)`：输入 ≈ `chars × 1.05 × min(1.6, 1.2 + 0.05×slide)`，
输出 ≈ 输入 × 1.3。`runs.cost` 列仍在，但按 Provider 的 `price_*` 折算，
默认 Provider 价格为 0。

### 6.5 错误分型与断点续翻

`llm/errors.py::classify_http(status, body)` 是唯一分类点：

| 触发 | 异常 | 处置 |
|---|---|---|
| 401/403 | `AuthError`(FatalRunError) | **暂停整个 Run**，不空烧重试 |
| 402 | `BalanceError`(FatalRunError) | 同上 |
| 429 | `RateLimitError`(Retryable) | 指数退避重试 |
| ≥500 | `ServerError`(Retryable) | 指数退避重试 |
| 400 + 内容策略关键词 | `ContentPolicyError` | **整批降级逐段**，只有真触发的段 failed |
| 其它 ≥400 | `ServerError` | 重试 |

- 重试：`engine._call_with_retry`，`retries=3`，`backoff=0.05 × 2^attempt`；
- JSON 解析失败 → 整批降级逐段；单段仍失败 → 段级 failed（`run_items` 记 error）；
- 取消：`cancel_event` 置位，未开始批次保持 `pending`，在途请求正常收货；
- 续跑：`start()` 只取 `status IN (pending, failed)` 的段，天然断点续翻。

### 6.6 线程模型（并发写库的护栏）

```
UI 线程 ──调用──▶ TranslationService.start()
                    └─ 新建 threading.Thread("run-N")
                         └─ asyncio.new_event_loop().run_until_complete(engine.run_translation)
                              └─ 所有 db 写经 Database._lock (RLock) 串行化
         ◀── Qt 信号 ── Bridge.progress / run_done（跨线程自动排队到 UI 线程）
```

- `Database` 用 `check_same_thread=False` + `threading.RLock`（**不是**独立写队列线程，
  与设计文档"单写队列"措辞不同，效果等价：所有写方法都 `with self._lock, self._conn`）；
- `PRAGMA journal_mode=WAL`、`foreign_keys=ON`；
- **UI 线程不得在翻译中直接写库**；要改段请走 Service 方法。


## 8. UI 层结构

`MainWindow` 用 `QListWidget` 侧栏 + `QStackedWidget` 注册 **6 个页面**

| 页面 | 文件 | 职责 |
|---|---|---|
| 项目管理 | `pages/projects_page.py` | 最近项目列表、新建向导（含密钥填写与连通性测试） |
| 项目工作台 | `pages/workbench_page.py` | 文件列表/标签/术语面板/导入文件与文件夹/开始翻译 + 预检 |
| 翻译进度 | `pages/progress_page.py` | 进度条、计数、token、取消 |
| 校对编辑器 | `pages/review_page.py` | 双栏表格、过滤、搜索替换、导出对话框、图片预览、术语一致性报表、注音编辑、**术语变更影响**（改术语译名后批量订正旧译文，可撤销） |
| 项目设置 | `pages/settings_pages.py::ProjectSettingsPage` | 语言方向/风格/Provider 覆盖/ruby 策略/滑窗 |
| 设置 | `pages/settings_pages.py::SettingsPage` | Provider 管理、并发、默认滑窗、获取模型列表 |

> 注：README 称"7 页面（含术语审核）"，但**术语审核是对话框**
> `pages/terms_dialog.py`（由工作台触发），不计入 `win.pages`。以代码为准。

**页面契约**（`pages/base.py::CtxPage`）：
- `needs_project = True`（默认）→ 无项目时 `on_enter()` 自动 `setEnabled(False)`；
- `on_enter()`：切到该页时调用（刷新/懒加载）；
- `on_project()`：项目打开/关闭后由 `MainWindow.refresh_after_project()` 广播调用。

**AppContext**（`app/context.py`）是唯一服务容器：
`cfg` / `project` / `bridge` / `importer` / `translation` / `review` / `exporter` / `run_handle`。
`open_project()` 一次性构造四个 Service；`close_project()` 会先 `run_handle.cancel()+join(10)`
再关库、放锁。

**Bridge 信号**（唯跨线程通道）：`progress(dict)` / `run_done(dict)` / `toast(str)`。
`progress` 事件的 `event` 字段取值：`tm` / `segment` / `segment_failed` /
`batch_policy` / `paused` / `finished` / `induction`。

> ⚠️ 只有 `ProgressPage` 连接了信号（`progress` / `run_done`）；**`toast` 全仓库从未
> `connect`**（13 处 `emit` 全部静默丢弃）——详见 §10.10 缺陷 ①。
> `ProgressPage._on_progress` 也只处理 `event == "segment"`，其余事件被忽略。

**各页生命周期实现实况**（有无调 `super()` 会影响"无项目时整页禁用"是否生效）：

| 页面 | `on_enter()` | 刷新内容 |
|---|---|---|
| ProjectsPage | 不调 `super()`，直接 `setEnabled(True)` | 重填最近项目列表 |
| WorkbenchPage | 调 `super()` | `_refresh_docs()` + `_refresh_gloss()` |
| ProgressPage | 调 `super()` | 从 `db.get_run()` 重建进度 |
| ReviewPage | 调 `super()` | `_rebuild_doc_combo()` + `refresh()` |
| ProjectSettingsPage | 调 `super()` | 回填项目配置 + 重建 Provider 下拉 |
| SettingsPage | 不调 `super()`，直接 `setEnabled(True)` | `_refresh()` + 并发/滑窗回填 |

`on_project()` 只有 Workbench / Review 显式重写（都等于 `on_enter()`），其余走基类。
`MainWindow._switch(row)` 是**先** `on_enter()` **再** `setCurrentIndex(row)`；
`refresh_after_project()` 对**全部 6 页**调 `on_project()`，与是否可见无关。

**线程模型实况**：`app/` 内**没有 `QThread`、没有 `QTimer`、没有 `QSettings`**。
唯一的两处后台线程是 `TranslationService.start()`（翻译）与
`WorkbenchPage._run_induction`（归纳，自建 `threading.Thread` + 函数内局部
`QObject` 信号 + 模态 `QProgressDialog` 忙等）。
而**向导与设置页的 4 处 `asyncio.run(...)`（拉模型列表 / 连通测试）跑在 UI 线程**，
网络请求期间界面冻结；`ReviewPage.refresh()` 更是每次搜索按键都同步查库（无防抖），
`ExportService.export()`（全文档重解析 + 渲染 + 写盘）也在 UI 线程同步执行。

### 10.8 疑似缺陷（源码核对发现）

> ⚠️ 其中 ① 的第 1 层、③ 已修复；逐项状态见 **§10.12 修复记录**。

> 这两条是本次架构通读发现的、**不在任何缺陷记录里**的问题，建议优先确认。

**① OCR 识别模型恒用中文（`src_lang` 未打通 + 引擎未接收 lang）**

这是**两层叠加**的问题，任何一层单独存在都足以让"按源语言选识别模型"失效：

**第一层：调用点从不传 `src_lang`。**
`OcrAdapter.parse` 支持 `opts["src_lang"]`，缺省用 `self.src_lang`；
而 `self.src_lang` 在 `adapters/__init__.py` 构造时取默认值 `"zh-CN"`：

```python
adapter = OcrAdapter()            # adapters/__init__.py:44 —— 不传 src_lang
...
src_lang = opts.get("src_lang", self.src_lang)   # ocr_adapter.py:115
```

但唯一的生产调用点 `ImportService.import_file`（`core/pipeline.py:56`）只传了
`opts={"ruby_loose": ...}`，**从不传 `src_lang`**：

```python
model = get_adapter(fmt).parse(dest, opts={"ruby_loose": project.ruby_loose})
```

**第二层：`RapidOCR()` 根本没接收语言参数。**

```python
def rapidocr_backend(img_path: str, src_lang: str = "zh-CN") -> list[str]:
    from rapidocr_onnxruntime import RapidOCR
    lang = _model_lang(src_lang)                    # "ch" / "japan" / "en" / "korean"
    if lang not in _OCR_INSTANCES:
        _OCR_INSTANCES[lang] = RapidOCR()           # ← lang 只当缓存键，没传进构造函数
    result, _ = _OCR_INSTANCES[lang](img_path)
```

`lang` **只被用作 `_OCR_INSTANCES` 的字典键**，`RapidOCR()` 是无参构造。
所以即使把第一层的 `src_lang` 打通，识别模型仍然是 RapidOCR 的默认（中文）模型。

后果：ja/ko/en 项目的图片一律用中文识别模型，准确率显著下降。而
`milestone-acceptance.md` 的 S1 声称"检测模型语言无关，识别模型按 src_lang 选择"，
README 与 ocr_adapter 的模块 docstring 也这么写——**两处声称都未落地**。

测试为什么没抓到：`test_ocr_backend_receives_lang` 注入的是**测试自己的** backend
（只断言收到了 `src_lang` 形参），而 `test_rapidocr_real_chinese` 只用中文图。
真正的 `rapidocr_backend` 从未在非中文场景下被验证。

修法：
1. 打通调用点——`ImportService.import_file` 显式传
   `opts={"src_lang": project.src_lang, "ruby_loose": ...}`（或给 `get_adapter` 加形参）；
2. 让 `rapidocr_backend` 真正按语言构造引擎——查 RapidOCR 的
   `rec_model_path` / `ocr_version` 等参数，把 `lang` 映射到对应的识别模型；
3. 补一条**从 `ImportService` 打进去**的回归测试（而非直接构造 `OcrAdapter`），
   并断言 `_OCR_INSTANCES` 的键与引擎参数随 `src_lang` 变化。

**② `get_adapter("img")` 在无 OCR 引擎时抛异常，会中断整个批量导入**

`OcrAdapter.__init__` 在 `get_default_backend()` 返回 None 时 `raise FormatError`，
而 `get_adapter` 把实例写进 `_ADAPTERS` 缓存是在构造之后——所以缺库时每次调用都抛。
`ImportService.import_files` 对每个文件 `try/except` 捕获，所以只影响该图片文件
（用户会看到"无可用 OCR 引擎"的明确指引），**不会**中断其他文件；
但整目录导入场景下每张图都会重复一条相同错误。建议确认这是期望行为。

**③ 同名文件重导入会丢掉该文件自己的全部译文 —— 与设计 §6.2 承诺相反**

设计 §6.2 与主文档 §8「增量使用」明确承诺：

> 已译文件被同名替换更新时，重新分段后**仅内容变化的段重译，未变段继续复用旧译文与人工修改**。

`ImportService` 的 docstring 也自称"含同名替换的增量重导"。

但 `Database.replace_segments` 的实现顺序让这件事**不可能发生**：

```python
self._conn.execute("DELETE FROM segments WHERE doc_id=?", (doc_id,))   # ① 先删掉本文件全部旧段
...
tm = self._conn.execute(
    "SELECT tgt_text,status FROM segments WHERE src_hash=? AND cfg_hash=? "
    "AND doc_id!=?", (b["src_hash"], cfg_hash, doc_id))                # ② 再查 TM，且排除本文档
```

①把本文件的旧译文删干净，②又显式排除本文档 → **同文件重导时 `reused` 恒为 0**，
用户更新一章后重导，该章**全部**段落回到 `pending`（而非只有改动段），
包括人工精校过的 `confirmed`/`human_edited` 内容，会重新计费并覆盖人工成果。

测试为什么没抓到：`test_replace_segments_tm_backfill` 断言的是 **doc2 复用 doc1** 的
跨文档复用（`reused == 3`），`test_tm_excludes_same_doc` 反而**明确断言**同文档
必须返回 `None`；全仓库没有任何测试覆盖"同文件重导复用"。

修法建议：在 `replace_segments` 开头（DELETE 之前）先把该文档的
`{src_hash: (tgt_text, status, ruby_map, review_flag)}` 快照进内存，回填时优先用快照、
再退回跨文档 TM。注意人工确认内容（`confirmed`/`human_edited`）必须优先于 TM，
且需要补一条"改一段、重导、断言未改段保住人工译文"的回归测试。

**④ 重导后 `run_items.segment_id` 变悬垂引用**

`replace_segments` 是 DELETE + INSERT，`segments.id`（AUTOINCREMENT）全部变化；
而 `run_items.segment_id` **没有外键约束**（DDL 里只是 `INTEGER NOT NULL`），
不会被级联清理。所以历史 Run 的 `run_items` 会指向不存在或**已被新段复用**的 id。
"查某 Run 的失败项再回查段落"这种用法会取到错误行。断点续翻本身不受影响
（`start()` 是按 `segments.status` 取段，不看 `run_items`）。

### 10.9 其他值得留意的实现细节（非缺陷，但会绊人）

- **provider 层零重试**：重试只在 `engine._call_with_retry`（`retries=3`、
  `backoff=0.05×2^n`）和 `term_induction._call`（`backoff=0.5×2^n`）。
  写新 provider 时**不要**自己加重试循环；
- **`json_mode` 三家支持不均**：OpenAI 发 `response_format={"type":"json_object"}`；
  Gemini 发 `generationConfig.responseMimeType`；**Anthropic 完全忽略该参数**，
  纯靠 prompt 约束——所以 Anthropic 上 JSON 解析失败的降级路径更容易被走到；
- **`classify_http` 的兜底偏宽**：所有未识别的 4xx（400 非策略、404、408、409…）
  都落到 `ServerError`（= 可重试），参数类错误会白重试 4 次；403 一律当鉴权失败；
- **Gemini 的 prompt 级拦截未映射**：只有 `promptFeedback.blockReason`、没有
  `candidates` 的响应会 `KeyError` → `ServerError`（重试 4 次后段级失败），
  而不是 `ContentPolicyError`；
- **`max_tokens` 不一致**：Anthropic 硬编码 8192，OpenAI/Gemini 都没设 → 长批可能被
  平台默认上限截断，表现为 `ResponseFormatError` → 逐段降级；
- **`update_segment` 无法把字段置回 NULL**（所有参数都是 `is not None` 才入 SET）；
- **白名单校验用的是 `assert`**（`set_doc_fields` / `update_run` / `update_segment` 的
  status）→ `python -O` 运行时会失效；
- **`db.execute()` 返回的游标在锁释放（且事务提交）后才被 fetch** →
  两个线程的"读—改—写"序列不原子；改并发逻辑时注意。
  `list_segments(search=...)` 的 `LIKE` 未转义 `%`/`_`；
- **No `UNIQUE(doc_id, seq)`**：seq 完全信任适配器，适配器出错会静默产生乱序/重复 seq；
- **无 WAL checkpoint / `busy_timeout`**：长期运行会累积 `-wal` 文件；
- **`QProgressDialog` 的两个坑（本次实测，写进度对话框时务必注意）**：
  1. **`close()` 会发出 `canceled` 信号**（Qt 在 `closeEvent` 里 `emit canceled()`）。
     所以"正常完成后的自动关闭"必须用一个独立的 `finished` 标志与"用户真的取消"
     区分开 —— 否则每次成功都会被误判成已取消（本次修复时先踩到、后在验证中抓出）；
  2. 反过来，**程序化调用 `cancel()` 在窗口尚未显示时不发 `canceled`**。
     因此取消逻辑不能只连 `canceled`，要直接连取消按钮的 `clicked`
     （本次改为 `prog.setCancelButton(QPushButton("取消"))` + `clicked.connect(...)`）。

### 10.11 适配层（`adapters/`）细节与边界

> ⚠️ ④（TM 复用不回填 `ruby_map`）已修复；①（`{0}`/`{r0}` 命名空间碰撞）
> 与 ②③⑤ 仍开放。逐项状态见 **§10.12 修复记录**。

**① 🟠 `placeholders_ok` 无法区分 `{0}` 与 `{r0}`（已实测）**

```python
_TOKEN_RE = re.compile(r"\{r?(\d+)\}")   # adapters/base.py —— r 是非捕获的可选前缀
tokens_of("{r0}") == tokens_of("{0}") == ["0"]
placeholders_ok("{r0}", "{0}")  # → True  ← 本应为 False
```

`{0}`（保护占位符，必须原样还原）与 `{r0}`（注音槽，按策略处理）在**校验层共用一个
数字命名空间**。后果：模型把注音槽写成了保护占位符（或相反）不会被判为可疑译文，
会直接落库；`drop` 策略下 `{r0}` 由 `_finalize_ruby` 剥离可以兜住，但
`keep`/`translate` 策略下的 `{0}`↔`{r0}` 混淆会污染输出。

修法：让 `tokens_of` 返回**带前缀的完整 token**（如 `"{r0}"` / `"{0}"`），
即改用 `_TOKEN_RE.findall` 的全匹配形式；注意这会让历史 `ruby_loose` 等路径的
行为变严，需同步跑 `test_ruby` / `test_engine` / `test_engine_ruby`。

**② 适配层边界（设计已声明 / 代码注释已标注，不是 bug）**

| 格式 | 边界 |
|---|---|
| 全部 | `seq` 由"同一源文件 + 同一算法"重放得出；**不可译段也占 seq**。归组键：txt/ocr 用 `meta["para"]`，md 用 `para+span`，html 用 `para+el_idx`，docx 用 `para` |
| txt | 孤立 `\r` 归一为 `\n` 但 eol 记为 `"\n"`（信息丢失）；空行成为 `kind="filler"` 透传段；输出恒 UTF-8；不支持 `bi_table` |
| md | "外层优先"→ `> `/`- `/`# ` 等结构标记进入送翻文本；front matter / 围栏代码 / html_block / hr 原样回放；行内代码正则不支持多反引号、`$...$` 不处理 `$$`；`bi_table` 丢弃原结构；**内联 `<ruby>` 已识别并原生还原**（§10.12 #15；此前完全不认，导致振假名策略失效） |
| html | **整个 `<a>` 被保护 → 链接文字不翻译**；`kind="pre"/"empty"` 段 render 完全不处理；**译文被当 HTML 解析（无消毒）**——模型返回的标记会进 DOM；注音锚定失败降级 `（rt）`；属性段（`alt`/`title`/`placeholder`）seq 排在所有块段之后 |
| docx | `_iter_para_chunks` **只读 `w:r` 直接子节点** → 超链接 / 域代码 / SmartTag 内文本不翻译；不处理嵌套表格、页眉页脚、脚注、文本框；无 ruby 段"整段套用主样式"（段内混排格式丢失）；有 ruby 段新 run 追加到段尾；`bi_table` 重建新文档丢样式；**无 mkdir**（依赖 `target/` 已存在） |
| img/ocr | 只做提取翻译，不做原图还原；**空行被丢弃（与 txt 的 filler 行为不一致）**；导出后缀非 `.md`/`.txt` 时**静默改成 `.md`** |

**③ 跨适配器的不一致（统一时注意）**

- 未知 `mode`：`md`/`docx` 抛 `FormatError`，txt/ocr 抛专属文案，**html 静默按 `target` 处理**；
- `bi_table` 仅 `md`/`html`/`docx` 支持；
- `restore_ruby(text, entries, rt_map, style_override)` 只在 `style_override="paren"`
  时输出 `（rt）`，**否则一律 `《rt》`**——包括 `style` 为 `"html"`/`"docx"` 的条目，
  与 ruby.py docstring「docx 风格默认按括号式还原」的表述不符
  （实际只有 docx 的 `bi_table` 显式传了 `style_override="paren"`）。

**④ ✅ TM 复用不回填 `ruby_map`（已修复）**

原 `db.replace_segments` 回填时只搬 `tgt_text` + `status`，不搬 `ruby_map`：
translate 策略下被复用的段落渲染时 `rt_map` 为空 → 回退成原假名注音。
现已把 `ruby_map` / `review_flag` 一并回填（同文件与跨文档两条路径都修），
回归测试见 `test_reimport_same_doc_reuses_own_translations`。

**⑤ `read_text` 的编码支持面**

仅 `utf-8-sig` / `utf-8` / `gb18030` 三种；含 NUL 字节直接判为二进制并抛
`FormatError("疑似二进制文件")`（审查第 4 轮统一加固，md/html 也曾缺此防护）。
GBK/Shift-JIS/Big5 等未覆盖（`gb18030` 是 GBK 超集，日文 Shift-JIS 不支持）。

## 11. 支持的文件格式（输入 / 输出）

### 11.1 输入（`adapters/__init__.py::_FORMAT_BY_EXT` 是唯一注册处）

| 格式族 | 扩展名 | 适配器 | 要点 |
|---|---|---|---|

| Markdown | `.md` `.markdown` | `md_adapter` | 保护行内代码/公式/图片/链接 URL；front matter 透传；aozora `《》` 与内联 `<ruby>` |

| Word | `.docx` | `docx_adapter` | 保留段落样式；表格逐格；原生 `w:ruby` 还原 |
| **EPUB** | `.epub` | `epub_adapter` | 复用 html 核心处理每个 XHTML 内容文档；其余条目原样拷回 |

### 11.2 输出

导出对话框的「导出格式」：`跟随源文件（默认）` / `txt` / `md` / `html` / `docx`。

- 选「跟随源文件」→ 写回**原格式**（含 epub / srt，这是它们的主要用法）
- 选具体格式 → 走 `_cross_format_export` **跨格式转换**（段级数据不变、按段落重排，
  源格式特有元素会丢失并给出 warning）；epub/srt **不支持作为跨格式目标**
  （`FormatError`：epub 需要重建容器、srt 没有时间轴），但 epub 源可以跨格式导出为
  md/txt/html/docx（有测试覆盖）

「导出模式」（各格式支持面不同）：

| 模式 | txt | md | html | docx | epub | srt | 图片 |
|---|---|---|---|---|---|---|---|
| `target`（仅译文） | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `bi_inter`（段间交错双语） | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `bi_table`（左右表格双语） | ❌ | ✅ | ✅ | ✅ | ❌ | ❌ | ❌ |

### 11.3 两个新适配器的关键设计

**EPUB**（`epub_adapter.py`，复用 `html_adapter` 的 `parse_tree` / `render_tree`）：

1. 从 `META-INF/container.xml` → OPF → **spine 顺序**取内容文档（阅读顺序，保证
   seq 分配确定）；OPF 坏掉则退回扫描 `.xhtml/.html` 扩展名。
2. **多个内容文档共用同一个 seq 空间** —— 经 `parse_tree(seq_base=...)` 偏移；
   `model.blocks` 是一条扁平序列，skeleton 里按 `(lo, hi)` 记录每个文档的段区间。
3. 三条硬约束：`mimetype` 必须是新 zip 的**第一个**条目且**不压缩**（用
   `zipfile.ZipInfo` + `ZIP_STORED`）；内容文档必须以**良构 XHTML** 写回 —— 所以用
   `etree.tostring(method="xml")`（HTML 方式会输出 `<br>` 破坏良构性）；
   `lhtml.document_fromstring` 会把根上的 `xmlns` 留成普通属性，XML 序列化后
   命名空间得以保留（有测试断言）。解析必须传 **bytes** —— 内容文档通常带
   `<?xml ...?>`，lxml 不接受带编码声明的 str。
4. 单个内容文档解析失败 → 跳过它、条目原样保留，不让整本书导入失败。
5. **已知边界**：`<a>` 与 html 一致整体作占位符（URL 防注入优先），因此
   **目录（nav.xhtml / NCX）与正文链接的文字不会被翻译**。若要翻译目录，需要把
   `flat()`/`_emit()` 的占位符机制扩展到"字符串占位符"并单独处理 NCX（NCX 不是
   XHTML，当前不在内容文档范围内）。

**SRT**（`srt_adapter.py`）：

1. **一个 cue = 一个 Block**，不调用 `split_long` —— 字幕的"时间轴 + 文本"是强绑定
   结构，cue 与译段必须 1:1，否则时间轴错位（代码注释里写明了原因）。
2. 模型是"按行无损切块"：空行与无法识别的内容都是 `translatable=False` 的 gap 块且
   **占 seq**；`meta` 存 `index`/`timing` 原文，render 逐块拼回 —— 未翻译时输出与
   源文件**逐字节相同**（含 CRLF、尾部换行、空行，有测试）。
3. 文本处理顺序不可调换：先 `rubyize_text(html=True)`（识别 `<ruby>`）**再**
   `ProtectMap` 保护 `{\...}` ASS 覆盖码与 HTML 标签 —— 反过来 `<ruby>` 会被标签
   保护正则整体吃掉、注音被当正文翻译。
4. `bi_inter` 是 cue 内逐行交错「原文行 + 译文行」（字幕常见双语形式）。
5. 已知取舍：超长 cue 不切分（>1500 字符整段送翻，不自动重排换行）；
   无空行分隔时，若文本行出现"纯数字行 + 下一行是时间轴"会被判为新 cue
   （乱序文件的容错代价）。
